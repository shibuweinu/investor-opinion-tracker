# 可恢复的雪球分页与可靠定时交付设计

## 目标

优化雪球高频账号深分页时的 HTTP 405/429、重复抓取和定时启动延迟问题，使早报、晚报和周报在
短暂上游异常、进程重启或 launchd 延迟启动后仍能尽量在当次任务完成；只有采集、核验和邮件投递
满足门禁时才推进报告检查点。

无法保证雪球或 SMTP 外部服务永远可用。本设计保证本地任务不会因分钟级启动偏差而漏跑，短暂
限流会在有界时间内重试，进程重启会从持久化断点继续，未通过门禁的结果不会伪装成正式报告。

## 方案选择

采用同步弹性执行，不引入常驻队列服务：

- 保持当前 Python CLI、外置 Chrome/CDP、宿主 Agent 和 launchd 架构；
- 每页持久化断点，限流时最长等待 10 分钟；
- 调度提供 15 分钟触发宽限；
- 使用运行锁和稳定运行 ID 保证同一报告周期只有一个活跃执行实例；
- 把核验、邮件发送、投递回执和报告检查点推进组合成单一交付命令。

不采用后台 worker 队列，因为它需要常驻服务、队列数据库和额外运维，不符合“克隆仓库即可使用”
的可移植目标。不拆分资讯号提前发送研究报告，因为这会违反当前任一配置账号采集不完整便禁止
正式投递的门禁。

## 运行标识与目录

每次计划任务使用稳定运行 ID：`<job-id>@<scheduled-cutoff>`，其中截止时间必须是配置中的计划时间，
不是 launchd 或 Agent 的实际启动时间。例如实际 21:02 启动的晚报仍使用：

```text
evening@2026-08-07T21:00:00+08:00
```

运行状态只保存在个人工作区，不进入产品仓库或个人远程配置仓库：

```text
.investor-opinion-tracker/runs/<run-id>/
├── run.json
├── lock
├── users/<user-id>.json
├── posts.jsonl
├── report.json
└── delivery.json
```

状态文件不得包含 Cookie、Token、密码、验证码或原始验证页面。写入采用同目录临时文件加原子替换；
损坏、版本不支持或账号清单不匹配的断点必须拒绝恢复并给出明确错误，不得静默混用。

## 分页状态模型

每个用户状态至少记录：

- schema 版本、运行 ID、用户 ID 和规范化主页 URL；
- 下一页页码；
- 已持久化帖子 ID；
- 当前最后一条非置顶普通帖的时间；
- 累计页数、请求次数和重试次数；
- 状态：`pending`、`running`、`complete` 或 `incomplete`；
- 最近一次可公开诊断的错误类型、HTTP 状态码和时间。

每页成功解析后先将新帖子按帖子 ID 写入持久化结果并更新用户状态，再请求下一页。恢复时从
`next_page` 继续，加载已持久化帖子 ID 去重，不重新请求已确认完成的页面。分页停止仍使用最后一条
非置顶普通帖与回溯截止时间比较，不能使用整页最小时间。单账号最大 300 页；达到预算必须标记
不完整，防止上游排序异常导致无限分页。

## 请求和限速

请求继续在用户已登录的外置 Chrome 页面内执行同源 `fetch`，继承浏览器授权会话，不从 Python
读取或导出凭据，也不伪造、破解雪球令牌。

- 普通研究账号：QPS 不超过 1，请求间隔 1.25–1.75 秒；
- `auxiliary_news` 资讯号：默认 QPS 0.4，请求间隔 2.75–3.25 秒；
- 旧任务草稿没有逐账号 QPS 时自动使用全局 QPS=1；
- 逐账号 QPS 由现有远程配置中的账号角色物化，不升级远程配置 Schema。

页面响应必须返回 HTTP 状态、可用的 `Retry-After` 和解析后的 JSON，不保存非 JSON 原文。成功页
沿用帖子 ID 去重、HTML 清洗、原文 URL、发布时间和置顶标记逻辑。

## 重试和恢复

以下错误允许在同一页重试：HTTP 405、429 和临时 5xx。优先遵循合法且不超过剩余预算的
`Retry-After`；否则使用 5、10、20、40、60、120 秒，之后固定 120 秒，并加入随机抖动。单账号
累计退避等待不得超过 10 分钟。

每次重试前重新打开对应用户主页以刷新同源页面状态，然后继续请求同一页。预算耗尽时保存当前
断点并返回 `incomplete`；下次相同运行 ID 从该页继续。401、明确登录失效、滑块或人机验证不自动
重试，立即保存断点并停止后续账号，等待用户恢复授权会话。

异常类别、HTTP 状态、重试次数、下一页和账号完成情况必须进入结构化运行结果，使 Agent、日志和
测试能够判断真实原因。临时接口错误不得只存在于进程内存。

## 调度宽限与并发

调度器使用 `scheduled-run` 作为唯一入口。它在读取个人远端配置和抓取前检查产品仓库：工作树必须
干净，先 fetch `origin/main`，仅允许 main 的 fast-forward 更新；更新后重新安装当前仓库并通过
`exec` 重启命令，避免旧进程继续使用已加载的旧模块。网络、分叉、安装或重启失败均失败关闭，
不得继续抓取、分析或投递。新设备使用仓库自带 bootstrap 后采用相同入口，因此功能更新机制可移植，
同时不把本机路径、凭据或 launchd 文件同步到代码仓库。

`jobs run-due` 将当前时间映射到最近的计划触发时间；只有当前时间处于 `[scheduled_cutoff,
scheduled_cutoff + 15 minutes]` 时任务到期。执行和分析均使用计划截止时间，禁止把 21:02 当成报告
行情截止时间。

同一运行 ID 使用非阻塞排他锁：已有活跃进程时，新实例报告“already running”并成功退出，不重复
抓取或发送；锁持有进程消失后允许新进程接管断点。不同任务或不同截止时间可以独立运行。

## 分析、投递与检查点

完整采集后按现有流程生成 `posts.json`、证据包和分析指令，由宿主 Agent 完成语义、事实和截止时间
行情核验。部分语义或事实核验可以通过逐项隔离生成 `ready_for_delivery=true` 的报告；采集不完整或
行情核验失败仍只能生成 `UNVERIFIED.md`。

新增一个幂等交付命令，输入稳定运行 ID、报告、核验 JSON、邮箱和任务信息，按以下顺序执行：

1. 校验 `status=complete` 且 `verification.ready_for_delivery=true`；
2. 校验报告运行 ID、任务 ID 和截止时间与当前运行状态一致；
3. 使用由运行 ID 派生的稳定 `Message-ID` 发送邮件；
4. SMTP 成功返回后原子写入 `delivery.json`；
5. 仅在回执存在且有效时推进报告成功检查点。

已有成功回执时命令不得重复发信，只验证并补推进缺失的报告检查点。SMTP 已接收邮件但进程在写回执
前崩溃的极小窗口采用“至少送达一次”语义：恢复后允许再次发送相同稳定 `Message-ID`，优先避免静默
漏报。不得宣称 SMTP 能提供严格全局 exactly-once 保证。

## 兼容与清理

- 现有 Schema v2 远程配置不迁移；
- 现有任务草稿、手动 `jobs run` 和非定时分析仍可运行；
- 没有新断点时从第一页开始；旧输出目录不能被误认为新断点；
- 成功与失败运行状态默认保留用于审计；仅由显式清理命令按运行 ID 或保留天数删除；
- 清理命令不得删除最终报告、远程配置或 SMTP 凭据。

## 测试与验收

自动化测试必须覆盖：

- 置顶帖不影响分页终止，跨页帖子 ID 去重；
- 每页成功后写断点，重启从已保存页继续且不重复请求早先页面；
- 405、429 和临时 5xx 按退避序列重试，恢复后继续同一页；
- 合法 `Retry-After` 优先，超预算值被限制；
- 资讯号使用较低 QPS，普通账号维持现有兼容行为；
- 401、登录失效和滑块不自动重试；
- 300 页安全预算和 10 分钟退避预算均能可靠终止；
- 21:02 匹配 21:00 任务，超过 15 分钟不会误触发，计划截止时间传入行情核验；
- 同运行 ID 并发互斥，失效锁可以接管；
- 采集不完整或行情失败禁止投递；
- SMTP 成功后写回执并推进检查点，已有回执不重复发送；
- SMTP 失败不写成功回执、不推进检查点；
- 旧任务和远程配置兼容。

完成标准：Ruff、mypy、完整 pytest 全部通过；在全新工作区物化个人远程配置后验证 09:00、21:00、
周日 18:00 计划识别；使用可控假响应验证断点恢复和投递幂等；真实雪球验收只在用户已授权登录会话
可用时进行，且不通过自动化绕过验证。
